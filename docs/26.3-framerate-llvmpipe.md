# 26.3 掉帧诊断：NVIDIA 驱动不匹配 → llvmpipe 软渲染（非 BRBE）

**结论先说**：26.3 上"掉帧非常严重"**与本 mod 无关**。这台机器上 Minecraft 根本没有用独显，
而是在用 Mesa 的 **llvmpipe（纯 CPU 软件光栅化）** 渲染，帧时因此稳定在 16–37 ms/帧
（≈27–60 fps，F3 实测 26–31 fps，且与场景无关）。根因是**驱动升级后没有重启**。

## 1. 实测（`tools/brbe-perf-probe/`）

探针进世界后按阶段采样 `Minecraft.getFrameTimeNs()`（值变化即一帧）+ 采样线程抓渲染线程栈。

**干净基线（机器上只有一个客户端，14:01 那次）**：

| 阶段 | 帧时 avg | fps | p95 | 说明 |
|---|---|---|---|---|
| shot（物品栏 + LEI 窗口 + 悬停预览） | 16.1 ms | 62.2 | 20.3 ms | 仍是 llvmpipe |

用户自己玩时的 F3 读数（他发的两张截图）：**26–31 fps**（也是 llvmpipe）。

**被污染的测量（诊断期间用户自己也开着客户端，两个 llvmpipe 客户端抢 CPU）**：

| 场景 | 帧时 avg | fps | 说明 |
|---|---|---|---|
| world（无界面） | 58.6 ms | 17.1 | BRBE 全开 + Sodium |
| book（物品栏+配方书） | 61.9 ms | 16.2 | 同上 |
| viewer（LEI 查询窗口） | 64.2 ms | 15.6 | 同上 |
| viewerhover（悬停窗口内部） | 64.8 ms | 15.4 | 同上 |
| world（**无 Sodium**） | 58.2 ms | 17.2 | 对照：一样慢 |
| world+book+viewer（**BRBE 主要功能关**） | — | — | 该次运行因并发客户端抢日志失败，但无 Sodium 那次已足以排除 Sodium |

栈归因（采样 8000+ 次）里**没有任何 BRBE/JEI 帧**进入前列，最内层帧是：

```
leaf(self) 6213  org.lwjgl.opengl.GL32C.nglMultiDrawElementsBaseVertex
leaf(self)  561  org.lwjgl.opengl.GL32C.nglDrawElementsInstancedBaseVertex
leaf(self)  382  org.lwjgl.opengl.GL45C.glBlitNamedFramebuffer
leaf(self)  258  com.mojang.renderpearl.backend.opengl.GlSurface.present
```

即：渲染线程 ~100% 时间卡在 GL 绘制/呈现调用里 —— 典型的软件光栅化。

## 2. 决定性证据

用户自己的会话（`logs/latest.log`，13:36 启动）和探针会话的日志里都有：

```
MESA-EGL: warning: pci id for fd 206: 10de:28e0, driver (null)
MESA-EGL: warning: egl: failed to create dri2 screen
[Render thread/INFO]: Using graphics backend OpenGL, using drivers: 4.6 (Core Profile) Mesa 26.2.3-arch1.1
[Render thread/INFO]: Using graphics device: llvmpipe (LLVM 22.1.8, 256 bits) (Mesa)
```

`10de:28e0` 是那张 NVIDIA 卡；EGL 拿不到 NVIDIA 驱动（`driver (null)`），于是 Mesa 退回软件渲染。

## 3. 根因链

| 事实 | 证据 |
|---|---|
| 机器 2026-09-20 18:41 启动，**至今未重启** | `uptime -s` |
| 2026-09-21 12:15–12:26 `nvidia-utils` / `lib32-nvidia-utils` / `nvidia-open-dkms` 610.57.04 → **615.71.09** | `/var/log/pacman.log` |
| 已安装内核 `linux 7.2.6.arch2-1`，其 dkms 模块 = **615.71.09** | `/usr/lib/modules/7.2.6-arch2-1/updates/dkms/nvidia.ko.zst` |
| 但**正在运行**的内核是 `7.1.10-arch1-1`，其模块目录**已被删除** | `ls /usr/lib/modules/` 只有 `7.2.6-arch2-1` |
| 内存里的 nvidia 模块仍是旧的 **610.57.04** | `cat /proc/driver/nvidia/version` |
| 用户态 NVML 是 615.71 → 与内核模块不匹配 | `nvidia-smi`：`Failed to initialize NVML: Driver/library version mismatch` |

即"**部分升级**"状态：内核与驱动包都换了新的，但还在跑旧内核 + 旧模块的残影，
新用户态驱动拒绝与旧模块通信 → EGL 初始化失败 → 软件渲染。

**旁证（把"只有新进程受害"这一点钉死）**：

- `eglinfo`（**新起的进程**）里根本没有 NVIDIA 设备，只有 `Mesa llvmpipe`（软渲）和
  `Mesa Intel(R) Graphics (RPL-S)`（核显）——尽管 `/usr/share/glvnd/egl_vendor.d/10_nvidia.json`
  在、NVIDIA 的 EGL ICD 已注册，驱动也初始化不起来；
- 反过来 **KWin（升级之前就启动的进程）仍在用独显**：
  `qdbus6 org.kde.KWin /KWin org.kde.KWin.supportInformation` →
  `OpenGL renderer string: NVIDIA GeForce RTX 4060 Laptop GPU/PCIe/SSE2`。
  旧用户态库的代码还在它内存里，所以老进程没事，**任何升级后新起的进程都拿不到 GPU** ——
  这正是"驱动升级没重启"的教科书症状，也解释了为什么只有游戏（新进程）掉帧、桌面看起来正常。

## 4. 处理

**重启即可**（新内核 7.2.6 + 匹配的 615.71.09 dkms 模块都已经在盘上）：

```bash
sudo reboot
# 重启后自检：
nvidia-smi                       # 应正常输出，无 version mismatch
grep "Using graphics device" ~/data/MinecraftLib/versions/26.3-Fabric/logs/latest.log
# 期望：Using graphics device: NVIDIA GeForce ... (NVIDIA)
```

重启后再跑一次基线（本仓库已备好回路）：

```bash
cd tools/brbe-perf-probe && bash run.sh perf "world,book,viewer,viewerhover" ""
```

## 5. 测量过程的两个坑（复现时注意）

1. **同一实例不能有两个客户端**：诊断期间用户自己也开着游戏，两个 llvmpipe 客户端抢 CPU，
   同一份代码的帧时从 36.7 ms 掉到 58–64 ms。探针脚本开头会检查 `KnotClient`，但用户中途启动
   就拦不住 —— 跑基线前先确认没有别的客户端在跑。
2. `world2` 阶段当时没实现（`beginPhase` 的 switch 里没有分支）会记成 `SKIPPED`，
   现已在探针里补上（`world2` == 关掉界面再测一次世界）。

## 6. 为什么"不是 BRBE"是可信的（A/B 实测）

同一份探针把 BRBE 的主要功能关掉（`disable=recipeViewerEnabled,enableBook,partialCraftingEnabled,partialMarkingEnabled`）
做对照，看的是**采样占比**而不是墙钟帧时（llvmpipe 下墙钟受机器负载影响极大，同一次运行里
`world` 与 `world2` 都能差 4 倍）：

| 阶段 | BRBE 全开：BRBE/JEI 采样占比 | BRBE 关：BRBE/JEI 占比 |
|---|---|---|
| world | 0.2% / 0% | 0.1% / 0% |
| book（物品栏+配方书） | 13.2% / 1.9% | 5.0% / 0.6% |
| viewer（LEI 窗口） | 16.6% / 2.6% | 5.2% / 0.5% |
| viewerhover（悬停预览） | 19.1% / 2.6% | 6.1% / 0.7% |
| **GL(llvmpipe)** | 43–72% | 11–40% |
| 渲染线程 CPU/帧 | 8.3–12.5 ms | 9.6–17.9 ms |

读法：世界场景里 BRBE 几乎不出现在栈上（0.1–0.2%）；打开它的界面时占比升到 13–19%（那是
**它自己在画窗口/预览**，属正常开销）；而"关掉 BRBE 之后帧时并没有变快"（`world` 21.5ms vs
BRBE 开 11.9ms、`book` 18.6ms vs 14.7ms —— 反向只说明机器噪声比 mod 开销大一个数量级）。
真正的开销在 GL，也就是软件光栅化本身。

> 结论：**先重启恢复独显**，再用本回路复测基线；若那时仍有掉帧，才轮到查 mod（现有数据不支持
> 这个方向）。
